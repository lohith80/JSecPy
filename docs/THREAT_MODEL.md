# JSecPy: Capabilities, Limitations, and Threat Model

A security tool must be honest about what it can and cannot prove. This
document states JSecPy's analysis guarantees, its blind spots, and the threat
model of the scanner itself.

## What JSecPy is

A static application security testing (SAST) tool for Java source. It parses
each file to an AST with `javalang`, runs a set of detectors, and reports
findings mapped to CWE and the OWASP Top 10. Injection-family detectors are
driven by an intra-procedural taint analysis; configuration and crypto
detectors are AST pattern matches.

## Analysis model and its limits (read before trusting a clean result)

**Intra-procedural.** Taint is tracked within a single method. Data that flows
out to a field, into a collection, or through another method is not followed.
A clean JSecPy result does **not** prove the absence of a vulnerability across
method boundaries.

**Flow-insensitive taint.** Within a method, JSecPy computes the set of
variables that can be tainted anywhere in the method (a small fixed point),
rather than tracking taint at each program point. This favours recall (fewer
false negatives) at some cost to precision. A variable reassigned from tainted
to safe may still be treated as tainted.

**Source/sink catalogs are finite.** JSecPy knows a curated set of servlet,
JDBC, crypto, and XML APIs. Framework-specific sinks (a custom DAO, an
in-house HTTP client) are invisible until you add them, which is exactly what
the YAML rule engine (`docs/WRITING_RULES.md`) is for.

**No type resolution / no build graph.** JSecPy does not compile the project
or resolve imports. Receiver types are inferred from local declarations only.
This is why some rules match on distinctive member names even when the
receiver type is unknown; it trades a few false positives for recall.

**Known blind spots** (tracked as issues, contributions welcome): reflection,
dynamic proxies, taint through arrays and maps (`map.put(k, tainted)` then
`map.get(k)`), a `StringBuilder` mutated across *separate statements* (chained
builder calls within one expression **are** tracked), cross-method flow, taint
stored to a field and read back in another method, `java.util.Random`
subclasses, annotation-driven frameworks (Spring MVC parameter binding), and
Lombok or other source-generating preprocessors.

**Validated against an adversarial corpus.** `tests/test_redteam_corpus.py`
holds 43 Java cases generated by a red-team pass (true positives, safe
negatives, and documented gaps). Every `detect` case must fire and every
`clean` case must stay silent in CI; the known gaps above are encoded as
`xfail` so they stay visible and flip to a failing test the day they are
closed.

**Bottom line:** JSecPy is a high-signal first pass and a CI gate, not a
proof of correctness. Confirm findings and pair it with review and DAST.

## Confidence semantics

- **HIGH** - attacker-controlled data provably reaches the sink under the
  taint model. Treat as a real finding to triage first.
- **MEDIUM** - a dynamically built (concatenated) value reaches the sink but
  taint could not be proven, or a configuration pattern that is usually but
  not always a bug. Review before acting.

## Threat model of the scanner

| Threat | Mitigation |
|--------|------------|
| A malicious file crashes the scan (parser bomb, weird encoding) | Each file is parsed in isolation; parse failures are recorded and the scan continues. A buggy rule is caught per-file and cannot abort the run. |
| A malicious file executes code during analysis | JSecPy only parses and inspects an AST. It never compiles, imports, or runs the target code. |
| Findings leak secret values into logs/SARIF | Secret detector output is masked; the raw secret is never emitted. |
| Suppression abuse hides real bugs | Inline `// jsecpy:ignore` and baselines are explicit and greppable; review them in code review like any other security exception. |
| Supply-chain risk in JSecPy itself | Minimal dependencies (`javalang`, `PyYAML`); CI runs on every PR; releases are pinned by tag in the GitHub Action. |
